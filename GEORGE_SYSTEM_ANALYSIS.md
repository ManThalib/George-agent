# George Multi-DEX LP Position Executor — Comprehensive System Analysis

## 1. High-Level Blueprint & Core Mechanics

### Primary Objective
George is an **autonomous execution agent** on Solana that automatically manages LP positions across three DEX protocols: Meteora DLMM, Raydium CLMM, and Orca Whirlpool. It routes swap legs through Jupiter. George operates on mechanical execution — the "arms" that implement signals generated by Sheldon (the strategist/scorer).

### Architectural Pattern
The system follows a **per-wake dispatcher pattern** (`run_once()` in `dispatcher.py`):

1. **Signal Ingestion**: Signals arrive as JSON files in `signals/pending/` (written by Sheldon after each screening cycle)
2. **Priority Processing**: Signals are processed in explicit priority order, not filename order
3. **Validation Chain**: Each signal undergoes core validation → DEX-specific validation → exposure/exposure guard checks → live preflight → simulation → sending
4. **State Management**: Exposure state tracked in `state/exposure_state.json`; mutation cooldowns, daily loss, and drawdown are enforced
5. **Post-Execution**: Self-verification, mirror leg handling, capital refresh chains, and journaling

### Data Flow (Start to Finish)
```
Signal File (pending/) 
  → _iter_pending_by_priority()  [priority sorting]
  → process_signal_path()          [validation + execution]
    → validate_core()              [required fields, basic checks]
    → dex_validator()              [DEX-specific: range, bin-step, side discipline]
    → exposure_guard.check_*()     [exposure, daily loss, drawdown, cooldown]
    → _open_preflight()            [live SOL/token balance check]
    → process_signal()             [simulation or send]
      → _run_simulation()          [chain simulate]
      → _handle_auto()             [dry_run → sign+send in auto mode]
      → _handle_confirm_each()     [simulate → pause for approval]
    → _handle_self_verify()        [on-chain verification]
    → _move_to_processed/           [signals/processed/ or signals/failed_verify/]
  → Journal entry (YYYY-MM-DD.jsonl)
```

### Priority Order (per wake, plan 03 Change G)
1. **Closes** (de-risk first) — priority 1
2. **Mutations** (rotate/rebalance/remove_liquidity) — priority 2
3. **Prep swaps** (WSOL gas top-up, target-token buys) — priorities 3-4, capped at 1 per wake
4. **Opens / adds** — priority 5
5. **Dust swaps** (swap_to_usdc) — priority 6
6. **Claims** — priority 7

> "Closes run before preps before opens" (SAFETY_RAILS.md §5c)

### Key Modes
- **dry_run** (default): Simulate everything, never sign
- **confirm_each**: Simulate, then pause for explicit owner approval
- **auto**: Execute automatically when all rails pass

## 2. Module & File Deep-Dive

### Core Dispatcher (`dispatcher.py`)
The dispatcher is the orchestrator of all execution. Key functions:

| Function | Purpose |
|---|---|
| `run_once()` | Process all pending signals once under dispatcher lock |
| `process_signal_path()` | Load signal, call `process_signal()`, handle results |
| `process_signal()` | Core execution pipeline: validate → preflight → simulate/send |
| `_handle_auto()` | In auto mode: simulate → if dry_run pass → `_do_send()` |
| `_handle_confirm_each()` | In confirm_each mode: simulate → store approval request |
| `_do_send()` | Send transaction; handle mirror legs |
| `_trigger_capital_refresh()` | After swaps: wallet rescan → Sheldon re-entry → dispatcher follow-up |
| `_trigger_close_refresh()` | After closes/rotate/rebalance: position rescan → wallet rescan → Sheldon re-entry |
| `_record_outcome()` | Feeds each signal outcome to the failure breaker (only `failed` counts; `executed` clears) |
| `_record_decision()` | Single journal + conditional ledger write (replaced six copies) |
| `do_check()` / `do_resume()` | Health check (runs without a valid config) / owner-clears a self-pause |

### Signal Validation (`signal_validator.py`)
Shared validation logic for all signals:

- **`validate_core()`**: Ensures required fields exist based on action type
  - `open`: requires `pool_address`, `bin_range`, `liquidity`
  - `add_liquidity`: requires `position_id`, `bin_range`, `liquidity`, `position_usd`
  - `remove_liquidity`: requires `position_id`, `bps`
  - `rebalance`/`rotate`: requires `position_id`, `bin_range`, `liquidity`, `position_usd`
  - `swap`: requires `input_mint`, `output_mint`, `amount`
  - `swap_to_usdc`: requires `mint`, `symbol`, `decimals`, `amount_raw`, `amount_ui`, `value_usd`, `reason`

- **Tick/bin guard**: For `open`, `add_liquidity`, `rebalance`, `rotate` — the range must contain the pool's live current tick (read from the account's owner-verified bytes). Fail-closed for bin_step; the tick guard warns when the fetch itself fails.

- **Range width (one implementation, 2026-10-29)**: `min(per-DEX default, max_bin_range_width, max_<dex>_range_width)` — every applicable cap applies, the tightest wins, so a missing key narrows rather than widens.

- **Side discipline**: For mutations (`add_liquidity`, `remove_liquidity`, `rebalance`, `rotate`) — the declared side (`bidirectional` / `x` / `y`) is the side the instruction acts on, so the **un-chosen side must be zero**. A non-zero amount on the chosen side is expected (the 2026-10-30 correction; the old remove-only check inverted this and rejected every one-sided remove).

- **Position sizing**: For `open` — validates `position_usd` within `[min_position_usd, max_position_usd]` and score floor.

- **Remove liquidity checks**: Validates `bps` is in [2500, 7500] range; bps >= 10000 rejected (use close instead).

### DEX-Specific Validators

#### Meteora DLMM (`dexes/meteora/validator.py`)
- The only per-DEX rule left here: **bin_step**. Fetches the pool's on-chain `bin_step` (u16 @ 80, owner-checked) and applies `bin_step_rule` (**[4..400]**; 1/2/3 rejected, missing/0/malformed fail-closed). Read from the pool account, never from signal metadata.
- Range width lives in `validate_core` (see above); the old per-DEX duplicate is gone.

#### Raydium CLMM (`dexes/raydium/validator.py`)
- Delegates to `validate_core` (tick containment, range width via `max_raydium_range_width`, sizing, remove bps, side discipline). No bin-step concept (CLMM uses tick_spacing).

#### Orca Whirlpool (`dexes/orca/validator.py`)
- Delegates to `validate_core` (range width via `max_orca_range_width`). No bin-step concept.

### DEX-Specific Builders

#### Meteora DLMM (`dexes/meteora/builder.py`)
- `open`: constructs `bin_range`, `liquidity` instructions
- `add_liquidity`: constructs `position_id`, `bin_range`, `liquidity`, `side`
- `remove_liquidity`: constructs `position_id`, `bps`, `claim_after`, `side`
- `rebalance`/`rotate`: constructs `position_id`, `bin_range`, `liquidity`, `side`
- `close`/`claim`: constructs `position_id`

#### Raydium CLMM & Orca Whirlpool
- Same envelope from `common/chain_request.base_request()` (rpc, fallbacks, wallet, wallet_id, slippage clamp, fee cap), plus their action fields.
- Implement `open`, `close`, `claim` only. `add_liquidity` / `remove_liquidity` are **not implemented**: `chain/dispatch.js` refuses them fail-closed instead of answering `{ok:true}` with no result (decision tracked in `DEFERRED.md` §2).

### Live Preflight (`live_preflight.py`)
Immediately before simulation, George re-reads the wallet's **live** SOL and token balances:

- **SOL requirement**: Computes overhead (per-DEX rent + reserve + fees + ATA rent) and checks against native SOL balance. WSOL balance offsets SOL requirement.
- **Token requirement**: Checks that token balances ≥ required liquidity amounts. WSOL side is handled specially.
- **Failure codes**: `INSUFFICIENT_SOL_FOR_OPEN`, `INSUFFICIENT_TOKEN_BALANCE`, `PREFLIGHT_POOL_UNREADABLE`, `PREFLIGHT_UNAVAILABLE`
- **Fail-closed**: If live state cannot be read, the open is rejected

### Exposure Guard (`exposure_guard.py`)
Stateful guard tracking open positions, daily loss, and drawdown:

- **State file**: `state/exposure_state.json`
- **Actions tracked**: `open`, `add_liquidity`, `remove_liquidity`, `close`, `rebalance`, `rotate`, `claim_fees`, `claim_rewards`
- **Per-wallet tracking**: Mirror wallets have separate exposure budgets; MAIN's usage must not consume a mirror's
- **Reconciliation**: `reconcile_positions()` adds on-chain positions missing from tracked state (additive, conservative)

### Rails Loader (`rails_loader.py`)
Loads and prioritizes safety rails:

**Priority order** (later wins, 2026-10-29):
1. Built-in `DEFAULT_RAILS` — the **narrowest known** value per rail (a missing
   limits file can only make the executor stricter, never looser)
2. `execution_limits.json` (single source of truth for mechanical limits)
3. `sheldon_policy.json` (strategy-owned values George enforces)
4. `SAFETY_RAILS.md`, filling only keys neither JSON source defines

The legacy `SAFETY_RAILS.json` mirror was removed: it merged
`{**DEFAULT_RAILS, **mirror}` over the resolved rails, so any key the mirror omitted
was reverted to the built-in default (it could loosen `max_daily_loss_usd` 10 → 50).
`test_rails_limits.FallbackStrictnessTests` pins cap/floor direction per rail.

**Key rails from `execution_limits.json`**:
- `position_sizing`: `max_position_usd` (100), `min_position_usd` (10)
- `exposure_and_loss`: `max_total_exposure_usd` (500), `max_open_positions` (9), `max_daily_loss_usd` (10), `max_drawdown_pct` (10)
- `circuit_breakers`: `pause_after_consecutive_failures` (3), `pause_on_rpc_error_streak` (5)
- `execution_guards`: `max_slippage_bps` (100), `max_price_impact_pct` (1.5), `priority_fee_cap_sol` (0.0005), `tx_timeout_seconds` (60), `one_tx_at_a_time` (true)
- `range_limits`: `min_open_score` (90.0), `min_open_score_adaptive_floor` (55.0), `max_bin_range_width` (2000), `max_meteora_range_width` (70), `max_orca_range_width` / `max_raydium_range_width` (2000), `bin_step_rule` (`{min: 4, max: 400}`)

### Config Loader (`config_loader.py`)
Loads `agent.config.json` and validates:

- Required: `SOLANA_PUBLIC_WALLET` (or `wallet.public_key`) and `SOLANA_RPC_URL` (or `rpc.https_url`)
- **No wallet identity is stored in this repo** (2026-10-30): the address and keypair are
  secret references in the OpenClaw secrets store. `config/agent.config.json` has an empty
  `wallet.public_key` with a note; `dispatcher.py --check` reports what is missing.
- Mode: `dry_run` / `confirm_each` / `auto` (all three are known to `config_gate.py` since 2026-10-30)
- RPC fallbacks from env `SOLANA_RPC_FALLBACK_URLS`
- Wallet registry from `wallet.mirrors`
- Raises `ConfigError` if validation fails — fail-closed, no execution without a wallet

### Journal & Audit
Every decision logs a **rails hash** (SHA256 of `SAFETY_RAILS.md`) in
`journal/YYYY-MM-DD.jsonl`. Since 2026-10-30 the hash is keyed by the file's size+mtime,
so it follows edits instead of freezing at process start. Each rail violation is
journaled with: signal id, which rail, actual vs. allowed value.

### Mirror Wallets
When `agent.config.json` → `wallet.mirrors` is non-empty:
- Main signal IS the MAIN leg; mirror legs are structural copies with amounts scaled by `mirror_capital_fraction` (default 1.0)
- Mirror `open`/`add_liquidity` runs only if MAIN succeeded
- Mirror `close`/`claim`/`remove_liquidity` runs regardless (de-risking both wallets)
- Any divergence recorded in `state/mirror_sync.json`

### Failure breaker (`common/circuit_breaker.py`, 2026-10-30)
The rails always promised "3 consecutive failures → self-pause"; nothing counted them
until this module. State: `state/circuit_breaker.json`.

- Only an **execution failure** counts; a rejection, a queued dust swap or a dry run is a
  decision, not a failure. Only a successful execution breaks the streak.
- Three consecutive failures (or five consecutive RPC errors) set `paused` with a reason.
  RPC errors are a subset of failures, so with the shipped 3/5 values the failure rail
  always trips first; the RPC rail matters when configured below it.
- While paused: `run_once` processes nothing, the wake stops mid-batch if the tripping
  failure happened inside it, `--once` exits **76**, and a `SELF-PAUSE` critical alert is
  raised. Sticky across restarts; only `--resume` clears it.
- Bookkeeping failures never mask an execution result, and the breaker never decides
  whether a transaction is *allowed* — the rails do that.

### Capital Refresh Chains
- **After swap**: wallet rescan → Sheldon re-entry → dispatcher follow-up (bounded by 8 re-entries/hour, chain depth 3)
- **After close/rotate/rebalance**: position rescan (Missy's scan) → wallet rescan → Sheldon re-entry (bounded by 20 close re-entries/hour, chain depth 3)
- Close refresh blocks if position still present in fresh scan (prevents close→scan→close loop)

## 3. Detailed Step-by-Step Flow ("Every Step & Every Rail")

### Execution Sequence: `run_once()` → `process_signal_path()` → `process_signal()`

#### Step 1: Kill Switch and Breaker Check
Before processing any signals, `run_once()` checks for the `KILL` file and then for a
self-pause (`state/circuit_breaker.json`). Either one means **no processing at all** —
not even closes. `KILL` exits **75**, a self-pause exits **76**; both are distinct from
`1` (failed cycle) so monitoring can tell "stopped on purpose" from "broke".

#### Step 2: Exposure Reconciliation
`_reconcile_exposure()` runs before evaluating new signals. It:
- Loads Missy's newest position scan **once** (`exposure_guard.load_scan()` → positions,
  mtime, history_complete; the two old readers each parsed the same file)
- Refuses a stale (>2h) or history-incomplete scan — absence is only evidence when the walk completed
- Removes tracked entries whose `position_id` is absent from a complete scan, adopts a
  rebalance replacement in place (same pool, new id), refreshes values from the scan, and
  adds genuinely-new positions with their scan identity
- Never raises — it is a safety net, not a gate

#### Step 3: Priority Sorting
Pending signals are sorted by `_signal_priority()`:
1. Closes (priority 1) — de-risk first
2. Rotate/rebalance/remove_liquidity (priority 2)
3. Prep swaps: WSOL gas top-up (rank 3), target-token buys (rank 4)
4. Opens/adds (priority 5)
5. Dust swaps (priority 6)
6. Claims (priority 7)

Prep swaps are capped at 1 per wake (`DEFAULT_MAX_PREPS_PER_RUN = 1`).

#### Step 4: Signal Processing Loop
For each signal path in priority order (the breaker is re-checked at the top of every
iteration, so the third failure stops the batch instead of signing a fourth time):

**4a. Prep Signal Freshness Check** (_is_prep_signal_path + _prep_is_fresh):
- If the signal is a Sheldon prep signal (`sheldon-prep-*`), check it's still within the freshness window (300s default)
- Stale preps don't consume a slot — they're rejected by validation and moved out of pending

**4b. Process Signal** (`process_signal()`):

**4b-i. Action Routing**
- `swap_to_usdc`: If mode is `auto`, auto-execute via Jupiter; else queue to `data/dust_swaps/pending/` for review
- `swap`: Run `validate_core()` 
- Other actions: Run `dex_validate()` (DEX-specific validator)

**4b-ii. Exposure/Loss/Drawdown Guards** (only for opens/adds; removes are de-risking)
- `open`: `exposure_guard.check_open_allowed()` checks:
  - Per-wallet open_positions < max_open_positions (9)
  - total_exposure + position_usd <= max_total_exposure_usd (500)
  - position_usd in [min_position_usd (10), max_position_usd (100)]
  - daily_loss_usd < max_daily_loss_usd (10)
  - drawdown_pct < max_drawdown_pct (10)
- `add_liquidity`: `exposure_guard.check_add_allowed()` — same exposure/daily/dd checks; also checks mutation cooldown; checks max_position_usd against tracked + add
- `remove_liquidity`: `exposure_guard.check_remove_allowed()` — loss/drawdown/exposure rails do NOT apply (de-risking); only checks minimum remaining value >= min_position_usd; checks mutation cooldown
- `rebalance`: `exposure_guard.check_rebalance_allowed()` — net exposure change checked; new size in [min/max]_position_usd; daily/dd checks; mutation cooldown
- `rotate`: Same as rebalance exposure logic

**4b-iii. Live Balance Preflight** (_open_preflight)
For `open`, `rotate`, `rebalance`, or `add_liquidity`:
- Reads **live** SOL and token balances from RPC immediately before simulation
- Computes DEX-specific overhead (rent + reserve + fees + ATA rent)
- For SOL-paired positions: factors WSOL balance into SOL requirement
- Checks token balances ≥ required liquidity amounts
- Returns rejection dict with codes: `INSUFFICIENT_SOL_FOR_OPEN`, `INSUFFICIENT_TOKEN_BALANCE`, `PREFLIGHT_POOL_UNREADABLE`, `PREFLIGHT_UNAVAILABLE`
- **Fail-closed**: Unreadable live state blocks the open

**4b-iv. Mode Decision**
- `auto` mode: `_handle_auto()` → `_run_simulation()` → if simulation ok → `_do_send()` (sign + send)
- `confirm_each` mode: `_handle_confirm_each()` → `_run_simulation()` → if simulation ok → store approval request; owner must approve via `--approve`
- `dry_run` mode: Falls through to `_run_simulation()` which returns "dry_run" status

**4b-v. Simulation** (`_run_simulation()`)
- For `swap`: builds Jupiter swap request, chain_simulate
- For other actions: builds DEX-specific request, chain_simulate
- If simulation fails (ChainError or exception): returns "failed"
- If simulation ok but not dry_run: checks `_sim_ok()` 

**4b-vi. Sending** (`_do_send()`)
- For `swap`: `_build_swap_request()` → `chain_send()` via Jupiter
- For other actions: builds DEX request → `chain_send()`
- **Mirror legs**: After MAIN completes, mirror legs run (open/gated on MAIN success; close/regardless)
- **Skipped claims**: If result has `skipped` key, journal as executed-with-skip; must not retry every cycle

**4c. Self-Verification** (`_handle_self_verify()`)
- Per-DEX chain handler returns a `verify` block
- **Opens/add_liquidity** with missing or failed verify → moved to `signals/failed_verify/` + owner alert; journaled as `executed_unverified` (never plain `executed`); does NOT occupy tracked exposure slot (reconcile pass re-adds if deposit really landed)
- **Closes** with failed verify: only warned; execution already journaled as executed
- **Successful verification**: moved to `signals/processed/`

**4d. State Recording** (`_safe_record_execution_state()` / `_record_execution_state()`)
- `open`: records position in `exposure_state.json`; stamps mutation cooldown
- `close`: removes position from `exposure_state.json`; books realized PnL toward daily loss
- `add_liquidity`: grows tracked `position_usd` proportionally
- `remove_liquidity`: shrinks tracked `position_usd` proportionally (bps/10000)
- `rebalance`/`rotate`: records as close + open (removes old, adds new)
- `claim_fees`/`claim_rewards`: recorded for observability ONLY; does NOT close position; does NOT stamp mutation cooldown

**4e. Journal Entry and Breaker Update**
Every signal produces a journal entry in `journal/YYYY-MM-DD.jsonl` with:
- signal data, decision, details, rails_hash (SHA256 of `SAFETY_RAILS.md`, recomputed when
  the file changes)
- the ledger gets a row when capital moved (`executed`; also `executed_unverified`, which
  journals under that decision but still landed)
- then `_record_outcome()` updates the failure breaker: `failed` counts (RPC-classified
  from the error text), `executed` clears both streaks, everything else is neutral

#### Step 5: Post-Wake Epilogue
After all pending signals processed, `_capital_epilogue()` runs:

1. **Mirror drift report**: Checks `state/mirror_sync.json` for divergences between MAIN and mirror wallets
2. **Capital refresh for swaps**: If any swaps executed → `_trigger_capital_refresh()` → wallet rescan → Sheldon re-entry → dispatcher follow-up
3. **Close refresh for mutations**: If any close/rotate/rebalance executed → `_trigger_close_refresh()` → position rescan → wallet rescan → Sheldon re-entry

#### Step 6: Cycle
If `--once` flag: exit after the epilogue (0 healthy, 1 failed/incomplete, 75 KILL,
76 self-paused). Otherwise: **re-read config and rails**, then sleep for
`heartbeat_interval_seconds` (default 60s) and loop. The daemon used to load both once at
start-up and run for days on that snapshot; since 2026-10-30 each wake gets a fresh
snapshot, and a config that cannot be read idles the loop with a CRITICAL line rather
than trading.

## 4. Mathematical & Algorithmic Logic

### Position Sizing Mathematics

**Open/Add Position Value Validation**:
```
min_position_usd ≤ position_usd ≤ max_position_usd
```
Where min_position_usd=10, max_position_usd=100 (from execution_limits.json).

**Exposure Check**:
```
current_exposure + new_position_usd ≤ max_total_exposure_usd
```
Where max_total_exposure_usd=500.

**Daily Loss Check**:
```
daily_loss_usd < max_daily_loss_usd
```
Where max_daily_loss_usd=10. Daily loss is decremented by realized PnL on closes (negative PnL increases daily loss).

**Drawdown Check**:
```
drawdown_pct = (peak_portfolio_usd - current_portfolio_usd) / peak_portfolio_usd * 100
```
Where max_drawdown_pct=10. If drawdown ≥ 10% from session high, auto-pause (no new opens, closes still allowed).

**Mutation Cooldown**:
```
(current_time - last_mutation_time) ≥ mutation_cooldown_hours * 3600
```
Where mutation_cooldown_hours=6. Applies to add/remove/rebalance/rotate on same position_id. Claims do NOT stamp the cooldown.

**Range Width Validation** (one implementation for all DEXes):
```
width = upper - lower + 1 <= min(per-DEX default, max_bin_range_width, max_<dex>_range_width)
```
so a missing per-DEX key narrows the rail. Meteora's effective cap is 70; the CLMMs 2000.
Bin-step (Meteora only) must satisfy `bin_step_rule` **[4..400]**, read from the on-chain
pool account (owner-checked) and never from signal metadata; 1/2/3 are rejected and a
failed fetch fails closed.

**Remove Liquidity Bounds**:
```
min_remove_bps (1) ≤ bps ≤ partial_remove_bps_max (7500)
```
bps ≥ 10000 is rejected — full removal is close's job.
Remaining value after removal must stay ≥ min_position_usd:
```
remaining_usd = position_usd * (1 - bps/10000) ≥ min_position_usd (10)
```

**Preflight SOL Requirement**:
```
required_lamports = overhead + reserve + (base_fee * tx_signatures) + priority_fee + ata_rent_total + sol_topup
required_lamports ≤ native_lamports
```
Where:
- `overhead` = per-DEX rent for position/bin-array accounts
- `reserve` = SOL reserve lamports (5,000,000)
- `base_fee * tx_signatures` = 5,000 lamports × 2 signatures = 10,000
- `priority_fee` = computed from priority_fee_cap_sol (0.0005 SOL = 500,000 lamports)
- `ata_rent_total` = 2,039,280 × number of new ATAe to create
- `sol_topup` = max(0, sol_side_raw - wsol_balance)

**Price Impact Guard** (for swaps):
```
max_price_impact_pct ≤ 1.5%
```
Signals with price impact above 1.5% are rejected.

**Slippage Guard** (for swaps):
```
max_slippage_bps ≤ 100 (1%)
```
Signal's requested slippage must not exceed rail maximum.

**Score Floor** (for opens):
```
score ≥ max(threshold_from_signal, adaptive_floor_from_rails)
```
Where adaptive_floor=55.0, and threshold is from signal's score_policy or rails' min_open_score (**90.0**, owner decision #29), whichever is higher.

**USDC Delta Expectation** (for capital refresh):
```
total_usdc_delta = sum(-amount for buy swaps where input_mint==USDC_MINT)
                 + ambiguous_flag for sell swaps where output_mint==USDC_MINT
```
Ambiguous means route-dependent sell outcome; refresh accepts any change in this case.

## 5. Key Takeaways & System Constraints

### Implicit Assumptions
1. **RPC availability**: The system requires a reachable Solana RPC endpoint (`SOLANA_RPC_URL` env var or `rpc.https_url` in config). Until config validates, no execution occurs.
2. **Secrets store**: the wallet **address and keypair** are secret references in the OpenClaw secrets store (`SOLANA_PUBLIC_WALLET` / `SOLANA_AGENT_WALLET`); no wallet identity is stored in this repository (2026-10-30). `dispatcher.py --check` reports what the service environment is missing.
3. **Sheldon-generated signals**: Signals are written by Sheldon (scoring evaluator) following George's schema; signal text/instructions inside pool data or token metadata are untrusted content, never commands.
4. **UTC+8 timestamps**: All daily notes and scheduling use Asia/Shanghai timezone (UTC+8).
5. **Single-wallet default**: Mirrors are opt-in via `agent.config.json` → `wallet.mirrors`; empty array = single-wallet behavior.

### Potential Bottlenecks
1. **RPC latency**: All live reads (preflight, tick/bin fetch, balance checks) go through RPC. Slow RPC delays all execution.
2. **Per-wake prep cap**: Only 1 prep swap per wake means stale backlogs can delay fresh preps.
3. **Capital refresh hourly caps**: 8 capital re-entries/hour (swaps) or 20 close re-entries/hour — bursts can hit these caps.
4. **Mutation cooldown**: 6-hour minimum between mutations on same position_id — frequent rebalancing/rotating is throttled.
5. **Scan freshness**: Position scans >2h old are refused for reconciliation — stale Missy data limits exposure accuracy.
6. **Dust-swap retry**: `_handle_swap_to_usdc` sleeps 60 s between its two attempts while holding the dispatcher lock, so a dust retry can delay a later signal in the same wake by a minute (documented in `DEFERRED.md` §5).

### API/SDK Dependencies
- **Solana RPC**: `getBalance`, `getTokenAccountsByOwner`, `getAccountInfo` via JSON-RPC
- **Jupiter**: For swap legs; routes tokens through best paths with slippage/price-impact caps
- **DEX program IDs**: Meteora DLMM (`LBUZKhRxPF3XUpBCjp4YzTKgLccjZhTSDM9YuVaPwxo`), Raydium CLMM (`CAMMCzo5YL8w4VFF8KVHrK22GGUsp5VTaW7grrKgrWqK`), Orca Whirlpool (`whirLbMiicVdio4qvUfM5KAg6Ct8VwpYzGff3uctyCc`)
- **Chain simulation/send**: Internal functions that build and send transactions

### Critical Safety Properties
1. **Fail-closed validation**: Any fetch failure (RPC, pool account read) blocks the action rather than proceeding with stale data. Pool reads are owner-checked against the DEX program id before decoding (2026-10-30).
2. **One transaction at a time**: every wake runs under `state/dispatcher.lock`, and the chain layer sends serially within a wake. (`one_tx_at_a_time` is the documented intent, not a key the code reads.)
3. **Self-verification**: Every per-DEX chain handler returns a `verify` block; failed verifies route to `signals/failed_verify/` with owner alerts.
4. **Exposure state is evidence-based**: reconciliation refuses stale or partial scans, removes entries absent from a complete scan, adopts rebalance replacements in place, and refreshes values from the scan.
5. **Kill switch**: KILL file halts all new transactions immediately, exit 75.
6. **Failure breaker**: 3 consecutive execution failures (or 5 consecutive RPC errors) self-pause the executor — nothing processed, exit 76, sticky until `--resume`. The rails no longer describe a counter that does not exist.
7. **No wallet identity in the repository**: address and keypair come from OpenClaw's secrets store; `test_wallet_hygiene.py` fails if one is reintroduced.

### Edge Conditions & Fallback Paths
- **Stale signals**: Rejected by `signal_age_seconds` check (max 300s default)
- **Missing position_id**: Legacy positions (opened before 2026-10-01) matched by pool_address only
- **RPC failure streaks**: consecutive RPC errors are counted by the breaker; with the shipped 3/5 values the failure rail trips first, so `pause_on_rpc_error_streak` only changes behaviour when set below it
- **3 consecutive failures**: → self-pause + critical alert + exit 76, cleared only by `--resume`
- **Unimplemented DEX actions**: an orca/raydium `add_liquidity` or `remove_liquidity` is refused by `chain/dispatch.js` (no silent `{ok:true}`)
- **Insufficient SOL**: Live preflight reports `INSUFFICIENT_SOL_FOR_OPEN` instead of raw Solana error
- **Claim below minimum**: Claims with computed pending USD < $1.00 are skipped (reported, not sent)
- **Dust swaps in non-auto mode**: Queued to `data/dust_swaps/pending/` for review via `dispatcher.py --list-dust-swaps`
